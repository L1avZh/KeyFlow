# Security

## Reporting a vulnerability

Please **do not** open a public GitHub issue for a security
vulnerability. Instead, email the address listed in this repository's
GitHub "Security" tab (Security Advisories), or open a private security
advisory directly via GitHub if you have access. Include:

- A description of the issue and its impact.
- Steps to reproduce (a minimal repro is enormously helpful).
- The KeyFlow version and platform.

We aim to acknowledge reports within 5 business days. This is a young,
small-maintainer project — please have patience, and thank you for
reporting responsibly rather than disclosing publicly first.

## Cryptographic design

| Purpose | Choice | Why |
|---|---|---|
| Key derivation | **Argon2id** (RFC 9106), 64 MiB memory / 3 iterations / 4 lanes by default | Winner of the Password Hashing Competition; the `id` variant resists both GPU/ASIC cracking (memory-hardness) and side-channel attacks better than Argon2d or Argon2i alone. Parameters follow OWASP's "high" guidance for a *local, offline* KDF — deliberately more expensive than a server-side login KDF, since the vault file itself is the only thing rate-limiting an attacker. |
| Authenticated encryption | **AES-256-GCM** | NIST-standardized AEAD; a single primitive gives confidentiality and tamper-evidence together (see THREAT_MODEL.md "why wrong password and corrupted file return the same error"). Implemented via the audited [RustCrypto `aes-gcm`](https://github.com/RustCrypto/AEADs) crate — KeyFlow does not implement any cryptographic primitive itself. |
| Randomness | `rand::rngs::OsRng` exclusively | Sources from the OS CSPRNG (`getrandom`/`/dev/urandom`/`BCryptGenRandom` depending on platform) for salts, nonces, and generated passwords. No userspace PRNG is used anywhere secrets are involved. |
| Nonce handling | Fresh random 96-bit nonce per encryption call, generated by `crypto::seal`, never reused | AES-GCM's security collapses if a nonce is ever reused under the same key; the API is structured so callers cannot pass in their own nonce. |
| Secret hygiene | `zeroize`/`ZeroizeOnDrop` on `VaultKey`, `Credential`'s password/notes fields, and intermediate decryption buffers | Reduces (does not eliminate — see THREAT_MODEL.md) the window secrets sit in memory after use. |

`unsafe_code = "forbid"` is set at the lint level in `keyflow-core`,
which has zero networking dependencies. This is the crate to read first
in any security review.

## Vault file format

```json
{
  "format_version": 1,
  "kdf": { "memory_kib": 65536, "iterations": 3, "parallelism": 4 },
  "salt": "<base64, 16 random bytes>",
  "verifier": { "nonce": "<base64>", "ciphertext": "<base64>" },
  "body":     { "nonce": "<base64>", "ciphertext": "<base64>" }
}
```

- `format_version`, `kdf`, and `salt` are plaintext by necessity — they
  are *inputs to* key derivation, not secrets themselves.
- `verifier` decrypts to a fixed constant and exists purely so an unlock
  attempt can fail fast without paying to decrypt a potentially large
  `body`. It is not a separate security boundary; a forged verifier that
  happened to decrypt would still fail when the real `body` didn't.
- `body` decrypts to the JSON-serialized list of credentials. This is the
  actual security boundary.
- Both AEAD calls bind a version-derived associated-data string
  (`"keyflow-vault-v{version}"`), so a ciphertext from one format version
  cannot be replayed as if it were another.
- Writes are atomic: content goes to a temp file, gets read back and
  verified to decrypt, and only then is `rename()`'d over the real path.
  A crash or power loss before that `rename()` leaves the previous good
  file untouched.

## Why there is no password reset

If KeyFlow could recover your vault without your master password, that
would mean *something else* — a recovery key stored somewhere, a
backdoor, a weaker derivation used only for the "forgot password" path —
could also decrypt it, which would make that something else an equally
attractive target and effectively lower the real security of the vault
to whatever protects the recovery path. KeyFlow doesn't build that path.
This is disclosed plainly during onboarding, not discovered the hard
way later.

## Quick unlock: a disclosed trade-off, not a vulnerability

KeyFlow can optionally store the master password in the OS's own secure
storage (Keychain on macOS, Credential Manager on Windows, Secret Service
on Linux) via the [`keyring`](https://crates.io/crates/keyring) crate, so
the user isn't forced to retype it on every launch. This is:

- **Off by default.**
- **Disableable at any time** from Settings, which immediately deletes
  the stored entry.
- **Automatically cleared and re-issued** whenever the master password
  changes, so a stale copy can never linger and silently stop working
  (or worse, silently keep working against an old password an attacker
  might have observed).
- Explicitly *not* an additional security boundary: anyone who can
  authenticate as the same OS user can read that keychain entry. This
  is stated to the user in the Settings UI before they opt in, not
  buried in documentation only. See THREAT_MODEL.md.

A biometric prompt on every unlock (Touch ID / Windows Hello) is
different from this — it would require the OS keychain entry to be
gated by a fresh biometric check each access, which the `keyring` crate
does not expose. That's tracked as a real, non-trivial platform-specific
feature in ROADMAP.md, not implemented today, and not something this
convenience feature should be confused with.

## Dependency and code auditing performed for this release

- `cargo test --workspace`: 47 tests in `keyflow-core` covering crypto
  round-trips/tamper-detection, vault lifecycle, domain-matching attack
  scenarios, and generator entropy guarantees, plus 4 tests in
  `keyflow-agent` covering native-messaging frame parsing (round-trip,
  clean EOF, oversized length prefix, truncated body). See CHANGELOG.md
  / the test files themselves for the full list.
- `cargo clippy --all-targets`: clean, no warnings, at the time of this
  release.
- `cargo audit` (RustSec advisory database), run against the full
  564-crate dependency tree (including the browser-extension native
  host's dependencies added since v0.1.0's initial cut):
  **zero known vulnerabilities**. Two
  non-vulnerability warnings, both in transitive dependencies pulled in
  by Tauri's own Linux GTK bindings, not by any KeyFlow code:
  `proc-macro-error` (unmaintained, RUSTSEC-2024-0370) and `glib`
  (an unsound iterator impl not exercised by anything in this codebase,
  RUSTSEC-2024-0429). Both are upstream Tauri dependency choices; re-run
  `cargo audit` periodically, since this is a point-in-time result, and
  revisit if either advisory escalates. This also runs in CI (see
  `.github/workflows/ci.yml`).
- Manual review for the OWASP-style categories in the project brief
  (hardcoded secrets, credential logging, command injection, path
  traversal, unsafe deserialization, insecure randomness, plaintext
  storage): no `unsafe` blocks exist in `keyflow-core`; no logging
  framework is wired in at all yet (so there is no logging call site to
  audit for leakage — see THREAT_MODEL.md); no shell commands are
  constructed from user input anywhere in this codebase; all file paths
  used for the vault come from the OS's own app-data-directory resolver,
  never from user-controlled strings; CSV/JSON parsing uses established
  crates (`csv`, `serde_json`), never hand-rolled parsers.
- **Not performed**: a third-party professional security audit. Nothing
  in this document should be read as "audited" in that sense — it's a
  disclosure of what the maintainers themselves checked.

## Browser extension: what it can and can't reach

The Chrome/Edge/Chromium extension (`browser-extension/chrome`) never
receives the master password or the derived vault key — see
ARCHITECTURE.md §4 for the full request path. Specifics that matter for
review:

- **The extension ID is pinned**, not left to whatever Chrome assigns an
  unpacked load. `manifest.json`'s `key` field is a real RSA public key
  whose SHA-256 hash Chrome uses to compute the extension ID
  deterministically (`lkljkibkbdbgjmljnhoioceloeiiigmj`), matching the
  `allowed_origins` entry in the generated native-messaging manifest. A
  different extension — including a modified copy of KeyFlow's own
  source without the matching private key — gets a different ID and the
  browser refuses to launch the native host for it. The private key
  itself is not needed for anything else and was not retained.
- **The native host (`keyflow-native-host`) holds no vault access.** It
  is a stateless stdio↔socket relay; compromising it (or replacing it,
  if an attacker already has write access to where it's installed —
  at which point far worse is already possible) gets you a relay to the
  same local socket described next, nothing more directly.
- **The local agent socket is a new, disclosed trust boundary**: same-OS-
  user only, no further authentication. See THREAT_MODEL.md's "local
  agent socket" entry and `agent_server.rs`'s module doc for the full
  reasoning, including the two mitigations that do apply (vault must be
  unlocked; `GetCredential` re-validates the origin server-side).
- **Not implemented**: Firefox and Safari support (different native-
  messaging manifest formats/transports), and any Chrome Web Store
  listing — this ships as a manually-loaded unpacked extension. Also
  not implemented: auto-launching the desktop app when the extension
  can't reach it, and locking down the local socket beyond OS-level
  same-user permissions (see ROADMAP.md).

## Android: security boundaries

The Android app (`android/`) reuses `keyflow-core` directly through a
thin UniFFI bridge crate (`crates/keyflow-mobile`) — the same Argon2id
KDF, AES-256-GCM AEAD, and vault-file format as desktop, called via JNA
from Kotlin, not reimplemented. `crates/keyflow-mobile` itself contains
no cryptography of its own (see its module doc comment).

- **Quick unlock** (`biometric/BiometricVaultUnlocker.kt`) stores the
  master password encrypted by an Android Keystore key that requires a
  fresh `BiometricPrompt` (`BIOMETRIC_STRONG`) authentication for every
  decryption (`setUserAuthenticationRequired(true)`, plus
  `setUserAuthenticationParameters`/`setUserAuthenticationValidityDurationSeconds(-1)`
  depending on API level — see the code comment for why two code paths
  exist). The key is invalidated automatically if the device's biometric
  enrollment changes. Same disclosed trade-off as desktop's OS-keychain
  quick unlock: anyone who can unlock the device can then unlock KeyFlow.
- **Autofill** (`autofill/KeyFlowAutofillService.kt`) runs in-process
  with the main app, sharing one in-memory vault handle — if the vault is
  locked, autofill defers to an unlock screen
  (`autofill/AutofillAuthActivity.kt`) before returning any value, never
  a cached or pre-decrypted credential. It only ever fills values into
  the field(s) the Android OS itself identified in the requesting app's
  view structure — this service does not use an Accessibility Service
  (broad, blanket access to on-screen content/events in every app),
  specifically because the OS-mediated Autofill Framework only exposes
  the one screen's structure for the one fill request, not standing
  access to everything.
- **Native-app origin matching is a heuristic**, unlike the
  cryptographically-exact web-domain matching used everywhere else in
  KeyFlow — see ROADMAP.md item #17 for the honest limitation.
- `android:allowBackup="false"` and empty `dataExtractionRules.xml`
  (both in `AndroidManifest.xml`) exclude the vault and preferences from
  Android's own backup/device-transfer mechanisms.
- `FLAG_SECURE` is set on the main window (`MainActivity.onCreate`),
  blocking screenshots/screen recording of vault contents and redacting
  the app's entry in the recent-apps switcher to its icon only.
- No `INTERNET` permission is requested at all.
- **Not yet verified**: none of the above has been exercised on a real
  device or emulator (see ROADMAP.md #16) — this section describes what
  the code does, not what a human has confirmed it does under real
  Android's actual enforcement of these APIs.

## Reporting checklist for reviewers

If you're doing your own review, the highest-value places to look are:
`crates/keyflow-core/src/crypto.rs` (the only file that should ever
touch a cryptographic primitive), `crates/keyflow-core/src/domain.rs`
(the phishing-resistance logic), `crates/keyflow-core/src/vault.rs`
(the on-disk format and atomic-write logic), and — new for the browser
extension — `apps/desktop/src-tauri/src/agent_server.rs` (what the local
socket will and won't release) and `browser-extension/chrome/src/
background.ts` (where the page's origin is determined). Everything else
in `apps/desktop/src-tauri` is IPC plumbing and OS integration around
that core. For Android: `crates/keyflow-mobile/src/lib.rs` (the FFI
boundary itself), `android/.../biometric/BiometricVaultUnlocker.kt`, and
`android/.../autofill/KeyFlowAutofillService.kt` +
`AutofillAuthActivity.kt` (origin resolution and the locked/unlocked
branch).
